# Архитектура — Meetup App (Telegram Bot + Mini App)

## 1. Общая схема

```
Telegram клиент
      │
      ▼
Telegram Bot (webhook)  ──────────────┐
      │                                │
      ▼                                ▼
Telegram Mini App (WebView)   Next.js API Routes (тот же проект)
      │                                │
      └───────────────┬────────────────┘
                       ▼
              Next.js Backend (единая бизнес-логика)
                       │
                       ▼
              Supabase (PostgreSQL + Auth + Realtime + Storage)
                       │
        ┌──────────────┼───────────────┐
        ▼              ▼               ▼
   Row Level      Realtime чат    Storage (фото)
   Security

Дополнительно, подключаются сбоку (не в основной бизнес-логике):
  Yandex Maps API   → карта и места
  Telegram Stars    → оплата подписок
  n8n               → уведомления, напоминания, service-автоматизации
  Vercel            → hosting и деплой
  GitHub            → репозиторий и CI
```

## 2. Почему один Next.js проект, а не бот отдельным сервисом

Бот Telegram обычно требует постоянного процесса (long polling) или webhook-эндпоинта.
Мы используем **webhook**, а не polling — тогда бот — это просто ещё один API route
(`app/api/telegram/webhook/route.ts`) внутри Next.js. Плюсы:

- Один деплой на Vercel вместо двух серверов.
- Общий доступ к Supabase, общим типам, общей бизнес-логике (лимиты, подписки).
- Serverless — не платим за постоянно работающий процесс бота.

Если в будущем нагрузка вырастет — этот webhook-хендлер можно вынести в отдельный сервис
без изменения остальной архитектуры (см. п.7 "Масштабирование").

## 3. Структура репозитория

```

  (app)/feed/            — лента "Сегодня рядом"
  (app)/map/             — карта активностей
  (app)/create/          — мастер создания встречи (шаги 1–8 из ТЗ)
  (app)/chats/           — список чатов + чат
  (app)/profile/         — профиль пользователя + "Мой пакет"
  admin/                 — защищённая admin-панель
  api/
    telegram/webhook/    — приём апдейтов от Telegram Bot API
    auth/                — валидация Telegram initData, выдача сессии
    events/              — CRUD встреч, лента, ranking
    applications/        — отклики на встречи (pending/accepted/rejected)
    subscriptions/       — тарифы, лимиты, статус подписки
    payments/telegram-webhook/ — обработка Telegram Stars платежей (источник истины)
    boosts/              — поднятие встречи
    reviews/             — отзывы после встречи, рейтинг
    reports/              — жалобы, блокировки
    admin/                — данные для admin dashboard

components/              — переиспользуемые UI-компоненты (по фиче)
lib/
  supabase/               — клиенты supabase (browser / server / service-role)
  telegram/               — валидация initData, работа с Bot API, Stars invoice
  scoring/                — алгоритм ранжирования ленты (п.19 ТЗ)
  validation/             — zod-схемы форм и API
  analytics/              — абстракция analytics-событий (провайдер подключаем позже)
types/                    — общие TypeScript-типы (в т.ч. сгенерированные из Supabase schema)
supabase/migrations/      — SQL миграции (нумерованные, накатываются по порядку)

tests/                    — unit и integration тесты критичной логики
```

## 4. Границы ответственности (что важно не перепутать)

| Слой | Отвечает за | НЕ отвечает за |
|---|---|---|
| Frontend (Mini App) | UI, отображение, локальная валидация форм | Проверку лимитов подписки, права доступа, подсчёт денег |
| Next.js API routes | Вся бизнес-логика: лимиты, права, ranking, статусы | Хранение секретов на клиенте |
| Supabase RLS | Последний рубеж защиты данных на уровне БД | Основная бизнес-логика (RLS — это защита, не workflow) |
| n8n | Уведомления, напоминания, необязательные для целостности данных сценарии | Списание денег, изменение статусов подписки, чат |

Это разделение — прямое следствие пункта 38 ТЗ ("нельзя рассчитывать subscription
permissions только на frontend", "нельзя делать основной чат через n8n").

## 5. Аутентификация

1. Telegram Mini App при открытии даёт `initData` (подписанную Telegram строку).
2. Frontend отправляет `initData` на `/api/auth`.
3. Backend **обязательно** проверяет HMAC-подпись `initData` секретом бота
   (алгоритм из официальной Telegram документации на момент реализации — см. `lib/telegram/validate-init-data.ts`).
4. Если подпись верна — backend создаёт/находит пользователя по `telegram_id`,
   выдаёт Supabase-сессию (или собственный signed cookie — решаем на этапе 3).
5. Все дальнейшие запросы идут с этой сессией; RLS в Supabase опирается на неё.

Никогда не доверяем `telegram_id`, `username`, фото и т.д., присланным с клиента
напрямую в обход этой проверки.

## 6. Ranking ленты (кратко, подробности в lib/scoring)

Скоринг — взвешенная сумма факторов (город, категория/интересы, свежесть,
расстояние, заполненность мест, boosted_at, коэффициент тарифа), а не
"PREMIUM всегда сверху". Коэффициент тарифа — небольшой множитель/бонус,
который **не должен** перебивать сильную релевантность бесплатной/START-встречи.
Точные веса — параметры, вынесенные в конфиг, чтобы их можно было подбирать
после запуска по реальным данным.

## 7. Масштабирование на будущее (iOS / Android / Web)

Вся бизнес-логика находится в API routes, которые ничего не знают о том,
что клиент — это Telegram Mini App. Контракт — обычный HTTP/JSON API.
Поэтому в будущем нативные iOS/Android/Web-клиенты смогут использовать
тот же backend, заменив только способ аутентификации (Telegram initData
→ например, Sign in with Apple / обычный email), не переписывая бизнес-логику.

## 8. Безопасность (сводно, детали в п.22 и п.38 исходного ТЗ)

- Все секреты только в `.env.local` (никогда в git, см. `.gitignore`).
- `SUPABASE_SERVICE_ROLE_KEY` используется только на сервере (в API routes),
  никогда не попадает в браузер.
- RLS включён на всех чувствительных таблицах.
- Подтверждение оплаты — только через серверную обработку Telegram-события,
  никогда через client-side callback.
